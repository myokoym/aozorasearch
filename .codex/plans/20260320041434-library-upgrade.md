# ライブラリアップデートとローカル検証 実装計画

> **エージェント向け:** 実装時は `superpowers:subagent-driven-development`（利用可能なら必須）または `superpowers:executing-plans` を使うこと。各手順はチェックボックス (`- [ ]`) で進捗管理すること。

**目的:** Aozorasearch の依存ライブラリをローカルで検証可能な状態へ更新し、最小回帰テストを追加し、新しい VPS へ移行する前提条件を整理する。

**要約**
- まず Bundler / lockfile と最小回帰テストを整備し、依存更新を安全に進める足場を作る。
- その後、`sinatra` / `rack` / `haml` / `kaminari` / `thor` / `launchy` / `nokogiri` を含む主要依存をまとめて更新する。
- Groonga 依存の強い gem は別バッチで扱うが、Web 起動経路と development 向け機能は主要依存更新の段階で必ず確認する。
- `bundle install` とテスト基盤が通っただけでは完了ではなく、主要依存更新と起動確認まで終わって初めて完了とみなす。

**完了条件**
- [ ] `bundle install` が Ruby 3.2 環境で安定して通る。
- [ ] `bundle exec rake test` が PASS する。
- [ ] `bundle exec ruby -I lib bin/aozorasearch version` と `bundle exec ruby -I lib bin/aozorasearch start --silent` が通る。
- [ ] Web の development 向け機能と新VPS前提条件が確認・整理されている。

**主要マイルストーン**
1. Bundler / lockfile と最小回帰テストの足場を作る。
2. `sinatra` / `rack` を含む主要依存を更新する。ここがこの計画の本丸。
3. Groonga 系依存を分離して更新・評価する。
4. CLI / Web 起動確認と VPS 前提条件の整理を終える。

**注意点**
- Task 1 と Task 2 が完了しても、それは依存更新の準備段階であり、まだ完了ではない。
- `sinatra` 系を据え置いたまま workaround を積み増すのではなく、まず依存整合を優先して確認する。

**方針:** まず Bundler と lockfile の状態を Ruby 3.2 環境で扱える形に整える。そのうえで Minitest と Rack::Test による最小テスト基盤を追加し、依存ライブラリを小さな単位で段階更新する。Groonga 依存の強い gem は別タスクに切り分け、ネイティブ依存の問題で全体が止まらないようにする。

**技術スタック:** Ruby 3.2.x, Bundler 2.x, Sinatra, Rack, Minitest, Rack::Test, Groonga/Rroonga
